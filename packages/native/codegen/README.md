# SwiftUI generation plan

## Baseline before SDK derivation

`Extract.swift` parses the SDK's SwiftUI, SwiftUICore, and framework overlay interfaces into declarations. `inventory.ts` normalizes them and checks availability. The generator then selects only names and signatures written in `catalog.ts`, `controlCatalog.ts`, `leafCatalog.ts`, `emitContainers.ts`, `emitSheet.ts`, and `emitPopover.ts`. A new view needs a constructor recipe, fields, a React adapter, a Fabric spec, and Swift hosting code. A new modifier needs a catalog selector, a transport field in a control or container, a TypeScript prop, and a Swift call. `swiftStyle` also needs a field, its native conversion, and an application call. The manifest reports declarations that are still unmapped; it does not bind them. `One.iOS` spreads `Swift`, so an emitted `Swift` member reaches both namespaces once exported. The generic leaf derivation introduced in `bf6713036` and wired in `2f766e892` derives Swift calls only after a person writes a leaf recipe. Coverage introduced in `d10d7834a` measures the gap but does not close it.

## Plan

1. Read public `View` methods and public view types from the SDK inventory. Classify parameters by the types the React Native bridge can represent directly: booleans, numbers, strings, and SDK enum values. Generate prop types, defaults, native conversion, and Swift application from those declarations. Prefer one SDK-selected signature per prop and fail on ambiguous overloads. Keep the iOS availability gate in generated Swift and the version metadata in the manifest.
2. Keep explicit overrides only for semantics absent from a signature: bindings and events, generic construction, view-building closures and slots, layout ownership, and values such as `Color` needing conversion. List each override category and its files below. `tabViewBottomAccessory` uses a view-building slot; its placement is an SDK environment value that accessory content can read.
3. Regenerate, typecheck, build a native consumer, and render an accessory plus two newly derived modifiers in an iOS 27 simulator. Record modifier counts before and after. Check generation for drift and run the native tests covering the touched interfaces.

## Semantic overrides

- Closures and bindings: `controlCatalog.ts`, `leafCatalog.ts`, and `controlTypes.ts` choose React events, controlled values, actions, and constructors with label or content closures. A Swift closure signature does not say which state React owns or when an event fires.
- View builders: `emitContainers.ts`, `emitSheet.ts`, and `emitPopover.ts` map React children to SwiftUI slots and own layout, presentation, and dismissal. Single-child `View` modifier names, parameter labels, required SDK enum arguments, Boolean bindings, and Swift calls are generated from the SDK. Distinct enum argument types give overloaded builders distinct prop names. `Swift.ViewSlot` applies these names to a base view using one `ViewSlot.Content` child and typed `options` when required. Binding options carry a value and `onChange` through the existing named native event shape. `Tabs.native.tsx` also accepts `Swift.TabViewSlot` with a generated tab modifier name and explicit content height; `OneNativeTabsView.swift` mounts the slot content. `TabViewBottomAccessory` still chooses inline versus expanded content from its placement environment. `emitContainers.ts` also declares the `NavigationStack` and `Toolbar` family: the stack hosts React Native children through a dedicated inline content child and reads `Toolbar` markers as SwiftUI `ToolbarContent`, and the three toolbar markers are one Swift view configured by kind.
- TabContent builders: `emitContainers.ts` declares `OneNativeTabs` with `swiftStyle`, so scalar TabView modifiers (`tabBarMinimizeBehavior`, `tabViewSearchActivation`, `defaultTabBarPlacement`) come from the SDK. `Tab` and `TabSection` are `TabContent`, which the `View` modifier derivation does not cover: `Tabs.native.tsx` validates their modifiers against the generated enums and sends them as one `tabModifiers` JSON prop per `OneNativeTab`, and `OneNativeTabsView.swift` applies each with its SwiftUI availability. `sectionActions` are native SwiftUI buttons that dispatch `onNativeTabsAction`.
- Generics and non-scalar values: `catalog.ts` supplies menu tree payloads, style conversions such as `Color` and `ShapeStyle`, and framework imports. Generic constraints do not identify the concrete React value or native conversion.
- Handwritten native hosts: `catalog.ts` retains `OneSwiftHost` and the two `OneNativeArrangement` hosts in the Fabric component provider map because they have no SwiftUI SDK view declarations.

SDK signatures cannot choose a React Native layout model or what React children feed a `@ViewBuilder`. These stay explicit. Scalar, URL, enum, callback, and binding modifier names and argument types come from the SDK. UIKit and PhotosUI cases imported through Objective-C come from their public SDK symbol graphs, cached per SDK version. Multiple bridgeable arguments use one generated object prop and an ordered native payload, including text lists and string sets. Generic and opaque style protocols use their SDK `Self == ConcreteStyle` cases to generate literal props and Swift calls. A single `Hashable` or `Equatable` value uses a string specialization; existing non-generic overloads keep their public prop names. Callback modifiers dispatch a named native event, including single and paired SDK enum values; bindings carry a controlled value and `onChange` callback through the same event path.

Public zero-argument `View` methods without generic requirements are derived as boolean enable props. This adds 17 names, including `hidden`, `labelsHidden`, and `compositingGroup`, with availability checks and framework imports for overlay methods. Callback and `Binding<Bool|String>` signatures with defaulted other parameters use one generated event transport. The same transport carries typed scalar callback values such as `onHover`. View builder slots with one content closure and any number of defaulted other parameters use one generated slot application method. Labeled scalar arguments, `Text` values, optional values, SDK enum cases, and framework overlay modifiers also derive from shared conversion rules. Optional values preserve an explicit `null` separately from an absent prop. More complex closure shapes, non-scalar bindings, layout rules for other ViewBuilder families, and generic constraints still need a hand mapping.

## Result

The iOS 27 SDK inventory now supplies parameterless public views, unambiguous scalar and enum `View` modifiers, bridgeable callbacks and bindings, and single-child view-builder slots. The generator emits their React props or slot names, native transport, Swift calls, and availability metadata. Derived style modifiers use one JSON field in the existing `swiftStyle` Fabric struct, so adding an SDK modifier does not add a C++ prop to every generated host. Swift applies only modifiers present in that field, in prop order.

`bun run coverage` reports 361 bound/generated modifier names out of 522 public `View` modifier names in the iOS 27 SDK (69%). It counts module/name pairs rather than overloads, across SwiftUI, SwiftUICore, and every installed SwiftUI overlay. Coverage was 51 bound names before this work, then 149 with the iOS 26 ceiling, 152 at the iOS 27 ceiling, 169 after parameterless methods, 177 after callback and binding transport, 181 after tab view slots, 208 after labeled scalars and `Text`, 216 after optional values, 246 after optional SDK cases and framework overlays, 248 after typed scalar callbacks, 260 after generated overload names, 303 after multi-argument scalar and enum records, 316 after generic style cases, 319 after nested static cases, 322 after generic `Hashable` values, 327 after URL values and optional actions, 330 after enum callback payloads, 335 after opaque style cases, 342 after general single-child view slots, 345 after omitting defaulted builder arguments, 346 after required SDK enum slot options, 350 after view-builder overloads and opaque builder closures, 352 after Boolean binding slots, 354 after text list and string set record arguments, 356 after generic `Equatable` string triggers, and 361 after imported framework cases. The three newly included iOS 27 modifiers are `defaultTabBarPlacement`, `presentationPlacement`, and `textInputBorderShape`. View coverage rose from 32 to 34 with `EditButton` and `EmptyView`.

The coverage target is every public module/name pair with at least one usable generated call. The remaining 161 names still need transport for richer values, bindings, closures, or child content. The next cheapest shared class is public cases in other imported framework symbol graphs where a remaining modifier takes one of those values. Bridgeable overloads get distinct prop names from their parameter labels or types while retaining the SDK method name in Swift. For example, `onOpenURLWithPerform` and `onOpenURLWithPrefersInApp` expose two SDK `onOpenURL` calls. A generated name without a working native call does not count.

`bold` and `tracking` are two previously unmapped modifiers exercised by `tests/native-features/app/one-native-autogen.tsx`. `tabViewBottomAccessory` now uses the generated slot call while its inline and expanded React content keep the placement environment mapping. The iOS 27 simulator proof shows expanded and inline placements. Native iOS CI now uses the Xcode 27 runner image, and `generate.ts` accepts iOS 27 symbols into checked-in bindings.
