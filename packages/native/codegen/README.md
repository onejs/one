# SwiftUI generation plan

## Baseline before SDK derivation

`Extract.swift` parses the SDK's SwiftUI, SwiftUICore, and framework overlay interfaces into declarations. `inventory.ts` normalizes them and checks availability. The generator then selects only names and signatures written in `catalog.ts`, `controlCatalog.ts`, `leafCatalog.ts`, `emitContainers.ts`, `emitSheet.ts`, and `emitPopover.ts`. A new view needs a constructor recipe, fields, a React adapter, a Fabric spec, and Swift hosting code. A new modifier needs a catalog selector, a transport field in a control or container, a TypeScript prop, and a Swift call. `swiftStyle` also needs a field, its native conversion, and an application call. The manifest reports declarations that are still unmapped; it does not bind them. `One.iOS` spreads `Swift`, so an emitted `Swift` member reaches both namespaces once exported. The generic leaf derivation introduced in `bf6713036` and wired in `2f766e892` derives Swift calls only after a person writes a leaf recipe. Coverage introduced in `d10d7834a` measures the gap but does not close it.

## Plan

1. Read public `View` methods and public view types from the SDK inventory. Classify parameters by the types the React Native bridge can represent directly: booleans, numbers, strings, and SDK enum values. Generate prop types, defaults, native conversion, and Swift application from those declarations. Prefer one SDK-selected signature per prop and fail on ambiguous overloads. Keep the iOS availability gate in generated Swift and the version metadata in the manifest.
2. Keep explicit overrides only for semantics absent from a signature: bindings and events, generic construction, view-building closures and slots, layout ownership, and values such as `Color` needing conversion. List each override category and its files below. `tabViewBottomAccessory` uses a view-building slot; its placement is an SDK environment value that accessory content can read.
3. Regenerate, typecheck, build a native consumer, and render an accessory plus two newly derived modifiers in an iOS 27 simulator. Record modifier counts before and after. Check generation for drift and run the native tests covering the touched interfaces.

For the `tests/native-features` iOS consumer, refresh React Codegen headers with `USE_FRAMEWORKS=static pod install` from `tests/native-features/ios` before building the workspace. A plain `pod install` cannot integrate its NitroWebImage and SDWebImage dependencies as static libraries.

## Semantic overrides

- Closures and bindings: `controlCatalog.ts`, `leafCatalog.ts`, and `controlTypes.ts` choose React events, controlled values, actions, and constructors with label or content closures. A Swift closure signature does not say which state React owns or when an event fires.
- View builders: `emitContainers.ts`, `emitSheet.ts`, and `emitPopover.ts` map React children to SwiftUI slots and own layout, presentation, and dismissal. Single-child `View` modifier names, parameter labels, required SDK enum, string, and Boolean arguments, Boolean bindings, and Swift calls are generated from the SDK. Hashable generic bindings beside a child builder specialize to strings. Direct generic `View` arguments use the same child slot when there is no builder overload. Distinct enum argument types and direct argument labels give overloaded slots distinct prop names. `Swift.ViewSlot` applies these names to a base view using one `ViewSlot.Content` child and typed `options` when required. Binding options carry a value and `onChange` through the existing named native event shape. Escaping zero-input `View` builders use the same child-slot path, deriving `sheet`, `popover`, and `fullScreenCover` presentation slots from their Boolean binding overloads. `Tabs.native.tsx` also accepts `Swift.TabViewSlot` with a generated tab modifier name and explicit content height; `OneNativeTabsView.swift` mounts the slot content. `TabViewBottomAccessory` still chooses inline versus expanded content from its placement environment. `emitContainers.ts` also declares the `NavigationStack` and `Toolbar` family: the stack hosts React Native children through a dedicated inline content child and reads `Toolbar` markers as SwiftUI `ToolbarContent`, and the three toolbar markers are one Swift view configured by kind.
- TabContent builders: `emitContainers.ts` declares `OneNativeTabs` with `swiftStyle`, so scalar TabView modifiers (`tabBarMinimizeBehavior`, `tabViewSearchActivation`, `defaultTabBarPlacement`) come from the SDK. `Tab` and `TabSection` are `TabContent`, which the `View` modifier derivation does not cover: `Tabs.native.tsx` validates their modifiers against the generated enums and sends them as one `tabModifiers` JSON prop per `OneNativeTab`, and `OneNativeTabsView.swift` applies each with its SwiftUI availability. `sectionActions` are native SwiftUI buttons that dispatch `onNativeTabsAction`.
- Generics and non-scalar values: `catalog.ts` supplies menu tree payloads, style conversions such as `Color` and `ShapeStyle`, and framework imports. Generic constraints do not identify the concrete React value or native conversion.
- Handwritten native hosts: `catalog.ts` retains `OneSwiftHost` and the two `OneNativeArrangement` hosts in the Fabric component provider map because they have no SwiftUI SDK view declarations.

SDK signatures cannot choose a React Native layout model or what React children feed a `@ViewBuilder`. These stay explicit. Scalar, URL, enum, callback, and binding modifier names and argument types come from the SDK. Cases and static or class values imported through Objective-C or other frameworks come from their public SDK symbol graphs, cached per SDK version. Multiple bridgeable arguments use one generated object prop and an ordered native payload, including text lists and string sets. Required bridgeable arguments can use SDK defaults for other arguments. Generic and opaque protocols use their SDK `Self == ConcreteType` cases to generate literal props and Swift calls; concrete overloads keep their public prop name. A public `RawRepresentable` type with a string `rawValue` initializer generates a string prop and native constructor. A modifier whose non-closure arguments all have SDK defaults generates a boolean prop when the argument types cannot be bridged. A single `Hashable` or `Equatable` value uses a string specialization; existing non-generic overloads keep their public prop names. Callback modifiers dispatch a named native event, including single and paired SDK enum values. Frozen enums with associated bridgeable scalars or points produce a typed case and value payload. Bindings carry a controlled value and `onChange` callback through the same event path.

Public zero-argument `View` methods without generic requirements are derived as boolean enable props. This adds 17 names, including `hidden`, `labelsHidden`, and `compositingGroup`, with availability checks and framework imports for overlay methods. Callback and `Binding<Bool|String>` signatures with defaulted other parameters use one generated event transport. The same transport carries typed scalar callback values such as `onHover`. View builder slots with one content closure and any number of defaulted other parameters use one generated slot application method. Labeled scalar arguments, `Text` values, optional values, SDK enum cases, and framework overlay modifiers also derive from shared conversion rules. Optional values preserve an explicit `null` separately from an absent prop. More complex closure shapes, non-scalar bindings, layout rules for other ViewBuilder families, and generic constraints still need a hand mapping. Zero-argument async actions on `task` and `refreshable` now emit an action identifier and await its JavaScript callback through one native completion registry. Async closures with one public SDK struct input now project its bridgeable fields and await the JavaScript callback; `onInAppPurchaseStart` supplies the product ID, type, name, description, price text, and family-sharing flag. Other async input and result shapes still need value conversion.

## Result

The generator emits their React props or slot names, native transport, Swift calls, and availability metadata. Derived style modifiers use one JSON field in the existing `swiftStyle` Fabric struct, so adding an SDK modifier does not add a C++ prop to every generated host. Swift applies only modifiers present in that field, in prop order.

The raw 522-name denominator includes SDK methods whose required inputs expose no public iOS value. For example, `scrollInputBehavior` requires `ScrollInputKind`, but every public case and factory for that type in the iOS 27 interface is unavailable on iOS. Those names cannot become working iOS props by generating a call from the public interface alone.

Bridgeable overloads get distinct prop names from their parameter labels or types while retaining the SDK method name in Swift. For example, `onOpenURLWithPerform` and `onOpenURLWithPrefersInApp` expose two SDK `onOpenURL` calls. A generated name without a working native call does not count.
