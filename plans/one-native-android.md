## Decision and evidence standard

**INFERRED recommendation:** Target Jetpack Compose, using **version-matched published source JARs as the declaration source of truth, with generated Kotlin calls compiled against the exact resolved Android artifacts as the correctness gate**. Extract with Kotlin compiler parsing and semantic resolution, rather than a text regex. Source JARs provide the default expressions missing from Kotlin JVM metadata. Keep the curated catalog: neither source nor bytecode can decide React prop semantics, controlled state, accessibility, or layout ownership.

**INFERRED biggest risk:** An RN subtree remains owned by Fabric while Compose determines its physical parent, size, and sometimes window. Incorrect ownership can produce stale layout, double event delivery, lost focus, or recycling a still-attached view. The evidence is the existing iOS slot contract and React Native's Android Modal implementation described below. This is a design risk, not an Android failure reproduced in this session.

- **INFERRED:** conclusion or proposed design derived from named inspected sources. All recommendations remain unimplemented.
- **GUESSED:** unverified prediction, including effort estimates. Cost bands mean relative engineering scope, not delivery promises.

## 1. Android's source of truth

### The candidates are different formats, not interchangeable API dumps

**RAN:** The JVM ABI dump example contains a method descriptor for `apply` with a Gradle Project argument, without a parameter name or nullable type contract. The tool documents its purpose as binary compatibility and is now in maintenance mode. AndroidX's inspected Compose signature file instead has named, source-facing Kotlin declarations alongside compiler-facing entries. Calling both “androidx binary-compatibility-validator `.api` files” hides the distinction. Sources: [validator documentation](https://github.com/Kotlin/binary-compatibility-validator), [actual JVM dump](https://raw.githubusercontent.com/Kotlin/binary-compatibility-validator/master/api/binary-compatibility-validator.api), [AndroidX Material 3 signatures](https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/material3/material3/api/current.txt), [Metalava format](https://android.googlesource.com/platform/tools/metalava/+/7a62d5ec56f03f4a73c69c71aacf59e91d8a40b5/FORMAT.md).

**RAN:** Kotlin's API explicitly says an ordinary parameter's default expression is unavailable in metadata. The annotation-constructor default-value API is a separate special case. Nullability has its own type flag. Sources: [KmValueParameter](https://kotlinlang.org/api/kotlinx-metadata-jvm/kotlin-metadata-jvm/kotlin.metadata/-km-value-parameter/), [isNullable](https://kotlinlang.org/api/kotlinx-metadata-jvm/kotlin-metadata-jvm/kotlin.metadata/is-nullable.html), [metadata reader](https://kotlinlang.org/docs/metadata-jvm.html).

**RAN:** The inspected source archive contains `commonMain/androidx/compose/material3/Button.kt`. Its Button signature includes `enabled: Boolean = true`, `border: BorderStroke? = null`, and `colors: ButtonColors = ButtonDefaults.buttonColors()`. It also has a composable content lambda with a RowScope receiver. This demonstrates names, nullability, literal defaults, expression defaults, and scoped content in an actual released artifact. The corresponding AAR has `classes.jar`; its `ButtonKt.class` contains the Kotlin metadata annotation descriptor. No `.api` or `current.txt` entry appeared in that AAR listing. This does not establish what every AndroidX artifact ships. Sources: [source JAR](https://dl.google.com/dl/android/maven2/androidx/compose/material3/material3-android/1.3.2/material3-android-1.3.2-sources.jar), [AAR](https://dl.google.com/dl/android/maven2/androidx/compose/material3/material3-android/1.3.2/material3-android-1.3.2.aar), [module JSON](https://dl.google.com/dl/android/maven2/androidx/compose/material3/material3/1.3.2/material3-1.3.2.module). Version 1.3.2 is an inspection sample, not a recommended dependency version.

**INFERRED:** No inspected binary dump or metadata format provides the complete `.swiftinterface` experience. Source JARs recover its useful input fields but require dependency resolution, source-set selection, and semantic analysis. A default expression is still not an evaluated default value: theme, composition locals, density, and function calls can determine the result. Preserve the expression for provenance; ordinarily let Kotlin execute it by omitting the argument. Do not translate Compose theme expressions into JS constants.

**INFERRED:** KLIB does not solve Android variant fidelity. Kotlin documents linkage metadata and serialized IR separately, marks several dump commands as debugging tools, and warns that Compose transformations can make IR and metadata signatures differ. Android-specific actual declarations must be checked against the Android artifact even when common source is shared. [Kotlin library format and commands](https://kotlinlang.org/docs/native-libraries.html).

### Proposed generation pipeline

1. **INFERRED:** Pin a supported resolved dependency set: Compose UI, foundation, Material 3, activity integration, Kotlin/Compose compiler plugin, and RN. Record Maven coordinates, selected variants, source and binary hashes, and compiler versions. A BOM alone is not the complete toolchain identity. Fail generation for an unsupported resolved set; never scrape moving `androidx-main` as a release authority.
2. **INFERRED:** Resolve the source artifacts matching those binaries. Parse only the allowlisted packages/modules. Use compiler semantic resolution for imports, aliases, overloads, generic bounds, implicit public visibility, extension receivers, and common/Android source-set relationships. Index by fully qualified source identity. Retain source location and default expression. Reject ambiguity and missing sources rather than inventing declarations.
3. **INFERRED:** Select catalog entries against that inventory. Keep Kotlin-specific recipes for content lambdas, scopes such as RowScope, callbacks, Modifier construction, state holders and opt-in APIs. Compose functions and Modifier extension functions are not SwiftUI constructors and View modifiers with renamed types.
4. **INFERRED:** Emit Fabric specs, public TS types/validation, Kotlin view managers/delegates and composable recipes, plus the required C++ state/descriptor integration for measured hosts and slots. Reuse the platform-neutral controlled event protocol; do not reuse Swift enum names as Android capabilities.
5. **INFERRED:** Compile all selected recipes and adapters against the resolved binaries with the Compose compiler. Include call shapes that omit optional parameters and explicitly pass nullable values. Validate exact inventory selectors as well: compilation alone may accept a different compatible overload after an upstream change. Source hashes expose expression-only changes that still compile. Compare deterministic generated outputs in CI.
6. **INFERRED:** Keep extraction and compilation as maintainer checks. Runtime users should consume generated code and locked support policy, without an AndroidX source scan on every app launch or JS bundle build. Cache inventory by the resolved artifact hashes.

**INFERRED:** Model omitted, explicit-null, and explicit-value props separately where the native API distinguishes them. Fabric transport defaults cannot erase this distinction. Choose a single presence representation in the catalog and emit it consistently. The inspected nullable/defaulted Button parameters demonstrate why “null means omitted” is unsafe as a general rule.

**INFERRED alternative, only if the owner chooses less tooling:** Use strict `kotlin-metadata-jvm` decoding of resolved binaries, plus classfile annotations, and record `hasDefault` without expressions. Omit defaulted native arguments and hand-curate the defaults of props actually exposed to JS. This still validates names/types/nullability/default presence and compiled recipes, but cannot explain or flag semantic default changes from metadata alone. This is a deliberately degraded design, not an automatic fallback when source extraction fails. It is likely enough for a small wrapper library; source JAR extraction is preferable for this project's stated provenance goal.

**GUESSED:** Source resolution and compiler analysis cost more initially than a Metalava signature parser. The unknown is how much tooling is needed to analyze selected source sets without reproducing AndroidX's entire build. Make a five-declaration inventory spike the first gate. If it cannot resolve Button, Text, Switch, a scoped container, and Dialog against pinned sources and binaries, revise this plan before catalog expansion. No such spike was executed here.

## 2. Runtime design and the parts that do not port

### Composition and lifetime

**RAN:** `ios/OneNativeComposition.swift` separates standalone hosting from composed publication. `OneNativeContainerView` owns an ordered child list, publishes `AnyView` values keyed by UIView identity, and creates one hosting controller when standalone. `ios/OneNativeHostingController.swift` walks the responder chain to find a UIViewController and performs containment.

**INFERRED:** Preserve the two rendering modes on Android. A standalone Fabric-managed wrapper owns a ComposeView. A composed node publishes observable props and a composable content function into the nearest native container; it does not instantiate another ComposeView. The parent invokes children under stable mount identities. Composables are functions participating in a composition, not retained View objects to move between parents. Changing parents may recreate composition-local remembered state, so controlled values must remain in the native model/React protocol.

**RAN:** Android documents ComposeView composition disposal strategies, including detachment and pooling behavior. The inspected ComposeView source requires view-tree lifecycle and saved-state owners. There is no UIViewController containment step. Sources: [Compose in Views](https://developer.android.com/develop/ui/compose/migrate/interoperability-apis/compose-in-views), [ComposeView implementation](https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/ui/ui/src/androidMain/kotlin/androidx/compose/ui/platform/ComposeView.android.kt).

**INFERRED:** Tie disposal explicitly to Fabric mount/recycle and the hosting lifecycle. Verify the RN Activity supplies the required owners and carry them into presentation contexts. Do not assume Fabric's recycling is recognized as Compose's pooling container. Define activation recursively from the live root, not merely “published once.” Deactivation must suppress events and presentations while preserving model state for a legitimate remove/reinsert.

**INFERRED:** Ordinary child composition needs Column, Row, Box and scoped composable calls. Subcomposition is a separate composition mechanism; SubcomposeLayout specifically lets measurement determine what to compose. Neither is a React renderer, a Fabric mounting bridge, or a solution to RN Yoga sizing. Avoid introducing SubcomposeLayout for an ordinary stack. Its intrinsic-measurement restriction makes it especially unsuitable as a universal measurement adapter. [SubcomposeLayout source](https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/ui/ui/src/commonMain/kotlin/androidx/compose/ui/layout/SubcomposeLayout.kt).

### Measurement: two independent layout owners

**RAN:** The iOS measured shadow node writes only Yoga height. `ios/OneNativeMeasuredComponentView.mm` suppresses nonfinite and near-identical reports. `oneNativeMeasured` obtains geometry from SwiftUI content with unconstrained ideal vertical sizing. The layout design records that writing both dimensions pinned width, and that a greedy Form has no useful intrinsic height. These are iOS observations from the prior work, not Android timing evidence.

**INFERRED:** Keep the ownership invariant: Yoga proposes available width; Compose measures content at that width; only the resulting content height returns to Yoga. Compose measures in physical pixels, so convert to RN logical units exactly once using density. Key reports to the mounted instance and width proposal so a delayed measurement cannot overwrite a newer width or recycled instance. Dedupe at pixel granularity. Respect parent min/max constraints and distinguish content-sized hosts from explicitly bounded hosts.

**INFERRED:** A Fabric wrapper must make its internal ComposeView measure the content with the real width and a content-height proposal, even when the wrapper's currently assigned Yoga height is zero or stale. Merely attaching `onSizeChanged` to a ComposeView that fills the current Fabric box reports the assigned height back to itself. Use Android's UI-thread measure/layout path with an explicit policy and capture the content result, then publish Fabric state. Do not synchronously call View measurement from a background Yoga measure callback. Verify that Compose's `requestLayout` reaches the wrapper after content-only changes; do not infer that RN's normal parent layout honors it.

**RAN:** Compose's `onSizeChanged` documentation warns that feeding its size into MutableState for layout causes recomposition in the succeeding frame. [Source documentation](https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/ui/ui/src/commonMain/kotlin/androidx/compose/ui/layout/OnRemeasuredModifier.kt). **INFERRED:** This is not proof of the latency of a Fabric state update, but it rules out assuming iOS's reported same-frame result carries over. Avoid a second Compose state feedback loop solely for height reporting. Android/Fabric convergence and first-frame behavior must be measured.

**INFERRED:** Do not promise content height for LazyColumn, scroll containers, fill-height content or arbitrary subcomposition. Give these a bounded viewport. Compose intrinsic-size queries are not a universal substitute for measuring under constraints; SubcomposeLayout explicitly rejects them. Android lacks a direct SwiftUI Form equivalent, so a form recipe should explicitly own grouped rows and scrolling rather than copying SwiftUI's measurement behavior.

### RN subtree inside Compose

**RAN:** `ios/OneNativeSlot.swift` wraps an existing UIView, reports a proposed box, and distinguishes passive/presented behavior. `cpp/OneNativeSlotShadowNode.h` pins slot size and absolute positioning. The layout design records a need to detach synchronously on Fabric unmount because SwiftUI dismantling happens later.

**INFERRED:** Use an explicit Fabric slot node with a dedicated Android ViewGroup containing the existing RN child views. AndroidView creates a small interop holder which hosts that Fabric-owned slot. Fabric retains logical child order, tags, reconciliation, and subtree lifetime; Compose owns the holder's physical placement. Do not create a second React root, recreate children in the AndroidView factory, or let Compose reuse one React subtree as another item.

**RAN:** AndroidView supports an existing View hierarchy through its factory/update integration and offers distinct reset/release callbacks for reuse. [Views in Compose](https://developer.android.com/develop/ui/compose/migrate/interoperability-apis/views-in-compose). **INFERRED:** Those callbacks handle the Compose holder lifecycle; they do not replace Fabric's unmount transaction. Detach the slot synchronously before Fabric recycling and clear holder references. Initially disable Compose view reuse for slots, while preserving normal React identity across presentation hide/show.

**INFERRED:** Start with one-way sizing: Compose allocates finite width and explicit height, reports that box to Fabric state, and Yoga lays out RN descendants within it. Use local coordinates inside the slot and explicitly convert window/ancestor coordinates for anchors and external measurement. A drawing result alone proves neither hit testing nor `measureInWindow` correctness. Content-sized RN slots require an additional natural-content measurement protocol and must not be implied by AndroidView `wrap_content`.

**INFERRED:** Automatic size would otherwise be circular: Yoga needs slot bounds to wrap RN content, while Compose asks that content for slot bounds. Break the cycle with a known width and separately measured inner content height, excluding flex-fill descendants from auto sizing. This is future work, common in concept with content-sized iOS sheets, and not a prerequisite for fixed slots.

### Presentations and input

**RAN:** Compose Dialog uses a Dialog wrapper and composes content into it; Popup is implemented with WindowManager integration. Sources: [Dialog](https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/ui/ui/src/androidMain/kotlin/androidx/compose/ui/window/AndroidDialog.android.kt), [Popup](https://raw.githubusercontent.com/androidx/androidx/androidx-main/compose/ui/ui/src/androidMain/kotlin/androidx/compose/ui/window/AndroidPopup.android.kt).

**INFERRED:** A popup's anchor-position policy and a dialog's separate window replace different parts of SwiftUI presentation. Material sheet states are not SwiftUI detents; define Android capabilities explicitly rather than pretending arbitrary iOS fraction/height detents are built in. Root composition context may be shared with a presentation, but View parentage and input routing still change. Treat IME insets, focus restoration, outside dismissal, Back and accessibility window focus as presentation responsibilities.

**RAN:** RN 0.86.2 `ReactModalHostView.kt` contains a DialogRootViewGroup implementing RootView, a JSTouchDispatcher, optional pointer dispatch, native-gesture forwarding, and a Fabric StateWrapper size update converting pixels to dp. It also forwards the test ID to the visible dialog root. [Version-pinned RN implementation](https://raw.githubusercontent.com/facebook/react-native/v0.86.2/packages/react-native/ReactAndroid/src/main/java/com/facebook/react/views/modal/ReactModalHostView.kt).

**INFERRED:** Use that RN version's Modal root contract as the reference for presented slots, not a generic Android touch listener and not a copied iOS touch-handler class. Bind the correct event dispatcher and surface identity. Assign exactly one RN event root for each slot: in-surface slots and window-presented slots need different routing decisions. Ensure a nested slot does not dispatch an event both locally and through the outer RN surface. Do not directly depend on Modal's internal constructor as a reusable public API.

**INFERRED:** The first future runtime gate should mount a content-sized native stack containing wrapping text, a controlled Switch and an explicit RN slot with Pressable/TextInput, then present the same kind of slot in a Dialog. Assert loaded state, actual geometry, exactly-once presses, accepted/rejected native changes, typing/focus, resize after a content-only update, unmount/reinsert, close/reopen and nested presentation. A negative control that reports the wrapper's assigned height must fail the wrapping-text check; one that removes presented event dispatch must fail RN presses. Measure idle layout/state-update counts and frame convergence. These are proposed checks, not tests run in this session.

## 3. Honest iOS critique

### 1. The public composition contract promises more than it implements

**RAN:** `codegen/emitControls.ts` emits public control props extending `Omit<ViewProps, 'children'>`; `codegen/emitContainers.ts` extends ViewProps too. `ios/OneNativeComposition.swift` renders composed content without displaying the child's UIView. The handoff explicitly records the loss of UIView-based testID, accessibility, background and layout behavior.

**INFERRED:** This is the highest-value repair. The same JSX prop can mean different things depending on ancestry, so types and runtime behavior disagree. Map a deliberate subset into SwiftUI semantics and modifiers, and reject unsupported composed props. Record the distinction in the schema so Android and Soot do not independently invent it. Accessibility labels/identifiers, disabled state and focus/measurement expectations should be explicit before advertising general ViewProps compatibility.

**RAN:** `src/Containers.native.tsx` only rejects a direct child whose React element type equals Form. It accepts arbitrary ReactNode children; the native container's `publish()` compact-maps noncomposable children away. **INFERRED:** A user component returning Form bypasses the direct-element check, and a plain RN child can disappear without explaining that Slot is required. I did not render those cases. Enforce container capabilities at the native composition boundary, where the actual mounted node is known; retain JS validation for useful early errors.

### 2. Measurement is under-built outside composed hosts

**RAN:** `codegen/leafCatalog.ts` gives standalone Text/Label default height 24 and Button 44; `codegen/emitControls.ts` has a catalog-driven height expression. Host measurement uses a different path, and the measured C++ descriptor always adopts reported height once present. The JS Host passes user style while its comment says Yoga must not receive a height.

**INFERRED:** Wrapping, large text, and explicit height/flex constraints need a published contract. A fixed standalone Text height can clip content even while the same Text measures correctly inside Host. That is a risk inferred from defaults, not a reproduced accessibility-font failure. Decide which leaves are content-sized and which controls need a bounded box; define precedence for explicit height/min/max/flex rather than letting state adoption settle it accidentally. Do this before adding content-sized presentations atop the same ambiguity.

### 3. The catalog is more than a mapping, and its validation guarantee is narrower than the headline

**RAN:** `catalog.ts` holds menu semantics and modifiers; `controlCatalog.ts` aggregates separate control catalogs. `presentationCatalog.ts` and `leafCatalog.ts` contain Swift recipes, JS validation strings, transport choices and sizing defaults. `generate.ts` also contains menu/tab rendering and output assembly, while containers and popovers have separate emitters.

**INFERRED:** Curation cost grows per semantic feature and supported interaction, not per Apple symbol. Each new family requires decisions about React state, callbacks, payload shape, unsupported modes, layout and native availability. The current factoring is reasonable for the covered families; a universal generator DSL would move the complexity without eliminating those decisions. Keep recipes readable and organize common transport/state emission only where it is actually repeated. Do not pursue a coverage percentage of the full SDK inventory.

**RAN:** `inventory.ts` selects constructors by short owner name and exact parameter label/type text. Modifier selection additionally matches normalized generic requirements. It stores default expressions but the selectors do not compare them; constructors do not compare generic requirements. `generate.ts` hashes entire interfaces and compiler/SDK provenance, derives enum values from the inventory, and typechecks assembled Swift. Containers are explicitly described in `emitContainers.ts` as structural rather than SDK bindings.

**INFERRED:** SDK extraction remains worth keeping: it rejects selected-signature drift and the assembled compile catches recipe mistakes. It does not prove behavioral parity, verify every recipe dependency with an exact selector, or guarantee default semantics. Whole-interface hashes can create output churn when an unrelated SDK declaration changes, while textual generic spellings can fail despite source compatibility. Separate deliberate SDK/toolchain upgrades from changes to the selected public contract; retain provenance, but make diagnostics show which selected declaration changed. Use fully qualified owners and constructor constraints as the selector model expands. Do not make downstream app consumers regenerate against arbitrary locally installed Xcode.

### Is the composition abstraction doing too much?

**INFERRED:** The core protocol is the right abstraction: return native declarative content, attach to a composition parent, detach. It preserves generated controls and avoids a second flattened control vocabulary. The standalone/composed distinction and shared container are justified by the layout design and current implementation. Generating 89 files is not itself evidence of over-engineering.

**RAN:** The same composition file also owns measurement decoration, child publication, hosting lifecycle and a no-op `setActive` hook. `composeInto` marks the immediate container active; `decompose` does not recurse through child views, while reset does. Publication rebuilds the child array after each insertion/removal.

**INFERRED:** The abstraction is under-specified at its boundaries, rather than fundamentally too broad. Clarify root activation, detach/reinsert, invalid child types, supported props and presentation cleanup. The code alone does not prove a detached descendant can emit an event, but it does show activation is not an explicit root-propagated contract. Add that scenario to future lifecycle validation. Do not turn this class into a universal presentation/navigation manager.

**INFERRED:** Rebuilding N published entries for each of N insertions creates quadratic publication work for an incremental mount. The loops in `insertChild` and `publish` establish that operation count; they do not establish a visible performance problem. **GUESSED:** It becomes material for large forms. Before lists/grids, measure mount cost and coalesce publication by mounting transaction if needed. AnyView erasure is a maintenance/performance question, not a demonstrated bottleneck here. Preserve one Fabric node per semantic control until measurements justify a different representation.

### UIKit escape hatch

**INFERRED recommendation:** Yes, with named native components and declared capabilities. Keep Fabric specs, TS validation, controlled events and schema generation shared; permit a curated UIKit implementation recipe. A SwiftUI signature must only be required for a SwiftUI recipe. Do not invent fake SwiftUI catalog declarations to wrap a UIScrollView or QLPreviewController.

**INFERRED:** For an inline zoomable image, use a bounded UIScrollView-backed implementation. A SwiftUI UIViewRepresentable adapter can satisfy `compositionContent()` while UIKit owns pan/zoom mechanics. Declare that it needs a viewport; do not ask a zoomable scroll view for an intrinsic content height. Define zoom/reset state and image loading lifetime once. This fits the current composition seam without making every control a controller abstraction. [UIScrollView zoom API](https://developer.apple.com/documentation/uikit/uiscrollview/zoom(to:animated:)).

**INFERRED:** A Quick Look presentation needs controller and data-source ownership, item identity, dismissal and resource lifetime. Its source-view transition hook is a controller integration boundary. Give a presenter a stable owner and explicit cleanup, separate from the inline composition parent's marker protocol. [Quick Look transition delegate](https://developer.apple.com/documentation/quicklook/qlpreviewcontrollerdelegate/previewcontroller(_:transitionviewfor:)).

**INFERRED:** UIKit's `UIViewController.Transition.zoom` belongs with the screen/presentation owner and a live source UIView. A composed control's backing UIView is not that visible source. Use an explicit visible anchor supplied through a representable if needed; do not infer it from the invisible Fabric node. The API is identified by [Apple's zoom transition documentation](https://developer.apple.com/documentation/uikit/uiviewcontroller/transition/zoom(options:sourceviewprovider:)); detailed One/react-native-screens integration was not inspected, so compatibility with the existing router remains **GUESSED**.

**GUESSED:** One bounded inline UIKit component is medium scope; controller presentation and interactive zoom transitions are medium-high to high scope. The lasting architecture cost is capability metadata (inline/presented, composable/bounded, commands/anchor requirements) and a small implementation-family split. A universal controller factory, arbitrary JS closures into UIKit, or a new navigation stack would cost much more and are outside this recommendation.
