# Independent review: automatic SSR external optimization

Verdict: APPROVE for merge as a framework fix. One minor non-blocking defect and one owed test cleanup are named below.

Scope read: owner direction in contrast plan; `packages/vxrn/src/plugins/autoDepOptimizePlugin.ts` current diff (committed during review as 40c7b29d4, blob 77de3b215, identical to the diff reviewed), `autoDepOptimizeExternal.test.ts`, scanner `scanDepsToOptimize.ts`, `mergeUserConfig.ts`, sole plugin caller `packages/one/src/vite/one.ts:454`, installed Vite `SSROptions` type (`external?: string[] | true`).

## What the change does

The plugin config hook now forwards `cfg.ssr.external` into `getScannedOptimizeDepsConfig`, where one `shouldOptimize` predicate filters both `ssr.optimizeDeps.include` and the generated `ssr.noExternal`: exact package match, `name + '/'` subpath prefix, and `external: true` excludes everything. Externals stop being forced into prebundling and stop being contradicted by an autogenerated `noExternal` entry.

## Evidence

RAN, from `packages/vxrn`: `tm window run heavy --local --narrow -- bun run test -- src/plugins/autoDepOptimizeExternal.test.ts` passed 2/2. The regression asserts through the actual Rolldown SSR optimizer `load` callback with positive controls (`internal-dep` and the similarly named `external-dep-extra` are bundled, runtime value 5), so the external negatives are not vacuous. Prefix logic is boundary-safe: `external-dep` does not capture `external-dep-extra`; subpath-only `external-dep/feature` leaves the root bundled and the feature external.

RAN, nearby suite: `autoDepOptimizePlugin.test.ts`, `scanDepsToOptimize.test.ts`, `mergeUserConfig.test.ts`, `ssrVendorOptimization.test.ts` passed 19/19. RAN `bun run typecheck` (`tsc --noEmit`) in `packages/vxrn`: clean.

TESTED with a disposable probe through the same real-server path (probe removed after the run, worktree verified clean for `packages/vxrn`):

- `ssr.external: true` bundled neither external nor internal dep and still loaded (value 2).
- Conflicting user `ssr.external: ['external-dep']` plus `ssr.noExternal: ['external-dep']` still did not bundle the external dep, because it is removed from the optimizer include list; internal dep still bundled, module loaded.
- Counterexample that failed: passing `external` only via plugin props bundled the dep anyway. Line 51 (`external: cfg.ssr?.external`) overwrites the spread `props.external` with `undefined` when the Vite config sets none. This makes the new typed `FindDepsOptions.external` field dead for direct plugin users. INFERRED non-blocking: no current caller passes it (the sole caller spreads `AutoDepOptimizationOptions`, which has no `external`), and direct `getScannedOptimizeDepsConfig` callers are unaffected. Owed one-line fix forward: `external: cfg.ssr?.external ?? props.external`.

## Simplification owed

`packages/vxrn/src/plugins/autoDepOptimizePlugin.test.ts` re-implements exclude filtering on local mock data and never calls the real function, so it can pass while the plugin breaks. Delete it in favor of the new integration regression, or rewrite it against real `getScannedOptimizeDepsConfig` calls. Pre-existing duplication also remains between this plugin's include-to-`noExternal` derivation and `deepMergeOptimizeDeps` in `mergeUserConfig.ts`; not introduced here.

## Remaining risks

INFERRED from Vite config-hook ordering: the plugin is `enforce: 'pre'`, so `ssr.external` contributed by a later plugin's config hook, or spelled only through the newer `environments.ssr` options, would not be seen. This matches the pre-existing limitation of the `optimizeDeps.exclude` reads in the same hook. INFERRED from scanner recursion: scanning still walks external packages, so a transitive dep of an external package can remain in the include list; that is wasted optimizer work, not a correctness break, since the external parent loads through Node.
