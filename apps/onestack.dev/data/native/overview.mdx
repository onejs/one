---
title: Native Overview
description: How One's native APIs are named, packaged, and linked
---

One ships native iOS and Android APIs alongside the framework. They cover
platform views (SwiftUI, Compose), shared views that work on both platforms,
and platform modules (notifications, clipboard, camera, and more).

All of them are reachable through the `One` namespace from the `one` package:

```tsx
import { One } from 'one'

One.UI.Image // shared by both platforms
One.iOS.Toggle // iOS only
One.Android.Switch // Android only
One.Notifications.schedule(...) // shared module
```

## Naming rule

The namespace tells you where an API runs:

- `One.X` is an API both platforms share: `One.Notifications`,
  `One.Clipboard`, `One.Network`, `One.Browser`, `One.Database`,
  `One.ImagePicker`, `One.AppInfo`.
- `One.iOS.X` is a platform framework in its own shape: SwiftUI views and
  UIKit-backed modules under the names and prop contracts Apple uses.
- `One.Android.X` is a platform framework in its own shape: Jetpack Compose
  views under the names and prop contracts Android uses.
- `One.UI.X` is views only: one component that renders through the native
  primitive on each platform (`One.UI.Image`, `One.UI.Map`, `One.UI.Icon`).
  A few shared hooks and state helpers live here too
  (`One.UI.useNativeState`, `One.UI.useSizeClass`).

Platform-only components stay strict: SwiftUI components throw outside iOS
builds and Compose components throw outside Android builds, so keep those
branches behind platform checks. Components that are only meaningful on one
platform but harmless elsewhere (toolbar, menu, zoom) return `null` instead,
so they are safe to keep in cross-platform trees.

## Packaging

The `one` package depends on `@vxrn/native`, which carries the native code:
iOS sources, Android sources, C++, and the generated bindings. Install `one`
and the native code comes with it, including the libraries One builds on
(Nitro Modules, Nitro Image, OP SQLite). There is nothing else to install.

Non-view modules (clipboard, haptics, notifications, and the rest) are Nitro
hybrid objects: a TypeScript spec in `packages/native/src/specs/*.nitro.ts`
declares the interface, and Nitrogen generates the Swift and Kotlin bindings.
Views are Fabric components: the specs in the same directory declare props
and events, and React Native codegen produces the native view managers. The
iOS controls mirror SwiftUI's names and prop contracts, and the Android views
mirror Compose's.

## Linking

The native code links during the native build through React Native
autolinking: `@vxrn/native` ships a podspec, an Android Gradle module, and a
codegen config, so `one prebuild` wires it into the generated Xcode and
Android Studio projects. Expo apps use Expo prebuild with the
`vxrn/expo-plugin` adapter instead; see
[Build or Run iOS](/docs/guides-ios-native) and [Ship with EAS](/docs/guides-eas).

Feature flags live in the app manifest under `native.app`. Examples: the
Android maps key (`android.googleMapsApiKey`), the camera permission string
(`imagePicker.camera`), push (`notifications.push`), and the
`SplitView` gamma flag (`ios.screensGamma`). Each page shows the keys it
needs. Without a key, the guarded call rejects or throws instead of crashing.

On web there is no native runtime. Shared views either render a web fallback,
render nothing, or throw; modules resolve inert values (denied permissions,
empty lists) or no-op. Each page documents its web behavior.
