---
title: Secure Store
description: Encrypted string storage in the iOS Keychain and under an Android Keystore key
---

`One.SecureStore` keeps small secrets: session tokens, refresh tokens, API
keys. On iOS each value is a Keychain item; on Android each value is
encrypted with AES-256-GCM under a key that lives in the Android Keystore and
never leaves the device.

Reach for it for anything you would not want in a plain file. For values that
need Face ID, Touch ID, or the passcode before each read, use
[Protected Store](/native/protected-store); for ordinary settings, use
[Storage](/native/storage).

## Usage

```tsx
import { One } from 'one'

async function signIn(token: string) {
  await One.SecureStore.setItem('session', token)
}

async function signOut() {
  await One.SecureStore.deleteItem('session')
}

function savedSession() {
  return One.SecureStore.getItemSync('session')
}
```

The async methods run off the JavaScript thread. The sync ones block it, so
use them for a value the first render needs, such as the saved session.

## How it works

**iOS.** Each key is a generic password item in the Keychain under the
service `One.SecureStore`, with the key as its account. Items are readable
while the device is unlocked. A write updates the item, or adds it when it
does not exist yet.

**Android.** One creates an AES key in the Android Keystore the first time
it writes. Each value is encrypted with a fresh 12-byte IV, which is stored in
front of the ciphertext in a private preferences file. Writes and deletes
commit to disk before they resolve, so a relaunch right after a write still
reads it. If the Keystore loses the key, as can happen after a restore, the
next write creates a new key and writes again under it.

**Both forms, one store.** `getItem` and `getItemSync` read the same items;
only the thread differs. Async calls run on a background thread; sync calls
run on the JavaScript thread.

**Errors.** A missing key reads `null`, and deleting a missing key succeeds.
Platform failures reject, or throw for the sync forms, with
`E_SECURE_STORE_GET`, `E_SECURE_STORE_SET`, or `E_SECURE_STORE_DELETE` as the
error's `code`.

## API reference

| Method | Returns |
| --- | --- |
| getItem(key, options?) | A promise of the value, or null |
| setItem(key, value, options?) | A promise |
| deleteItem(key, options?) | A promise |
| getItemSync(key, options?) | The value, or null |
| setItemSync(key, value, options?) | Nothing |
| deleteItemSync(key, options?) | Nothing |

Every method takes Expo SecureStore's options. `keychainService` names a
separate store: the keychain service on iOS, the Keystore key alias on
Android; an item written under a service is read and deleted with the same
one. `keychainAccessible` is iOS's item accessibility as a string:
`'whenUnlocked'` (the default), `'whenUnlockedThisDeviceOnly'`,
`'afterFirstUnlock'`, `'afterFirstUnlockThisDeviceOnly'`,
`'whenPasscodeSetThisDeviceOnly'`, `'always'`, or `'alwaysThisDeviceOnly'`;
Android accepts and ignores it, as in Expo. `accessGroup` is the iOS keychain
access group.

`requireAuthentication` binds the item to the user's biometrics:
`authenticationPrompt` is the message shown. On iOS the item gets a
`biometryCurrentSet` access control, so reads and updates prompt. On Android
its key requires authentication for every use and is invalidated when
biometrics change, after which the value can no longer be read. An
authenticated item answers a plain `getItem` too (with a prompt), and writing
one mode replaces the other. On Android the prompt needs a foreground screen,
so the sync methods throw for an authenticated item; use the async methods.
Deletes never prompt. From Expo, rename `setItemAsync(key, value, options)`
to `setItem` and replace each numeric accessibility constant with its string:
`SecureStore.WHEN_UNLOCKED` is `'whenUnlocked'`.

## Platform differences

| | iOS | Android | Web |
| --- | --- | --- | --- |
| Storage | Keychain | Encrypted preferences | None, rejects |
| Key | The Keychain's own | Keystore AES key | |
| Readable | While unlocked | After first unlock | |
| After uninstall | Can remain | Removed | |

## Limits and gotchas

- **Keep values small.** It suits tokens and keys. Large values cost a
  Keychain or cipher round trip on every read.
- **Strings only.** Keys must be non-empty strings and values strings;
  anything else throws before reaching native code.
- **Locked iPhones cannot read.** Items are readable only while the device is
  unlocked, so a background task that runs before first unlock gets a
  failure, not a value.
- **iOS Keychain items can outlive the app.** Deleting the app does not
  delete its Keychain items, so a reinstall can find an old session. Clear
  stale secrets on first launch if that matters.
- **Backups do not carry Android secrets.** Generated Android apps set
  `allowBackup` to false. If you turn backup on, the preferences file
  restores without the Keystore key, and reads fail with
  `E_SECURE_STORE_GET` until the value is written again.
- **Web never stores secrets.** Every method rejects, or throws for the sync
  forms, because anything kept in the browser would sit in plain text.

## Examples

### Restore a session on launch

```tsx
import { useState } from 'react'
import { One } from 'one'

function useSession() {
  const [token, setToken] = useState(() =>
    One.platform === 'web' ? null : One.SecureStore.getItemSync('session')
  )
  return {
    token,
    async save(next: string) {
      await One.SecureStore.setItem('session', next)
      setToken(next)
    },
    async clear() {
      await One.SecureStore.deleteItem('session')
      setToken(null)
    },
  }
}
```

The one sync read decides the first screen without a loading state. Writes
stay async, and the web check keeps the hook from throwing in a browser.

### Recover from a failed read

```tsx
import { One } from 'one'

async function readToken(): Promise<string | null> {
  try {
    return await One.SecureStore.getItem('session')
  } catch (error) {
    if ((error as { code?: string }).code === 'E_SECURE_STORE_GET') {
      await One.SecureStore.deleteItem('session')
    }
    return null
  }
}
```

A value that cannot be decrypted, such as one restored without its key, is
deleted so the app asks people to sign in again instead of failing on every
launch.
